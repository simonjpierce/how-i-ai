# Your first month

What to switch on, in what order, so a new setup gets to the good stuff quickly: real work on day one, a coordinator and specialist agents from the start, and none of the clutter a long-running system accumulates.

This is an idea file. Paste it into your AI agent — Claude Code or Codex — and it'll walk you through it in stages, adapted to your work. (It has to be an agent that can create files on your machine — a plain chat assistant can't set this up.)

## The core idea

The rest of this collection describes about forty capabilities, and it's easy to read it as a list to work through. Don't. A system built feature by feature, before there's work for each feature, collects tools nobody uses. The fastest route to a capable setup is the opposite: start with your **real projects** on the first day, so you see what the system can do on work that matters to you, and learn to drive it on that work. Switch on each further piece when the work asks for it.

Two things go in from the very first session, because everything else rests on them. The first is the rule that **everything is written down as you go**, so the knowledge lives in files and not in any one conversation (see [teach it who you are](./02-teach-it-who-you-are.md)). The second is the **agent structure**: one coordinating session that runs your work, and specialist agents for your main areas, from day one rather than as an advanced add-on. Starting with the structure keeps each conversation small and focused from the outset, which is both cheaper and sharper than one long chat that tries to hold everything.

## How it runs

**Day one: the foundation and one real piece of work.**
- Install the stack ([set up the stack](./01-set-up-the-stack.md)) and run the interview ([teach it who you are](./02-teach-it-who-you-are.md)), with "write it down as you go" as the first rule.
- **Back up to GitHub straight away.** A free GitHub account, a private repository for your vault, and one private repository per analysis project, so notes, code and cleaned data are versioned, backed up and easy to share with a co-author. Your AI sets up the command-line tool and does the commits; you approve the sign-in in your own browser. (More in [an undo button for your vault](./an-undo-button-for-your-vault.md).)
- **Install the quick save first.** A one-command mid-session save that brings your notes current, backs everything up and hands you a command to compress the conversation ([the session loop](./the-session-loop.md)). It's what makes the writing-down actually happen.
- **Start the agent structure.** Open one session as your **chief of staff**: it keeps the list of your projects and what's next on each, starts one session per project when work is needed, checks what those sessions produce, and hands you one thing at a time ([the agent fleet](./the-agent-fleet.md), [running many sessions at once](./running-many-sessions-at-once.md)). Give it a written brief and a projects list on day one. Then write a brief for each specialist agent your work needs: for a researcher, that's a [science agent](./a-science-agent.md) whose rules every research session reads. Each agent is a role defined in files (what it's for, its rules, what it must ask you about), not a separate program.
- **Do one real task end to end**, in a project session the chief of staff starts: a short, cited summary from your own papers, a first analysis step in a lab notebook, a document you need anyway. Correct it; the corrections become rules.

**Week one: bring in your material.**
- **Your literature.** Start with the twenty or thirty papers that matter now, not the whole library ([the reference library](./the-reference-library.md)). If your papers are a folder of PDFs and a half-used reference manager, that's normal: convert in batches as you need them.
- **One notebook per analysis** ([lab-notebook analysis](./lab-notebook-analysis.md)), opened before the first step, so every result is written down as it's produced.
- **A weekly check** run by the chief of staff: is each project's status still true, does each lab notebook have entries since its last code change, is everything pushed to GitHub, and how much of the week's usage has gone.

**Weeks two to four: let it learn you.**
- Corrections you make twice become written rules ([memory and context](./memory-and-context.md)).
- Add a specialist agent for another area only when there's a steady stream of work in it.
- Automate a task only after you've done it by hand three times and the steps have stopped changing ([growing your own capabilities](./growing-your-own-capabilities.md)).

**Not yet.** Overnight workers ([the overnight workhorse](./the-overnight-workhorse.md)), and the multi-model review panel ([the model panel](./the-model-panel.md)). Each earns its place once you have enough going on that planning and waiting on the work are themselves a cost.

**On a smaller plan.** The structure is what makes a smaller plan workable. Run the chief of staff at low effort, since its job is reading and routing rather than heavy thinking, and project sessions at medium. Split heavy jobs (reading thousands of images, reviewing a whole manuscript) across several days, and keep an eye on the week's usage in the app's settings ([managing your token budget](./managing-your-token-budget.md)).

## What this does *not* do

It doesn't set up everything in this collection, and it shouldn't: most of it waits until your work asks for it. It doesn't choose your projects or your methods; it gets the scaffolding out of the way so you're working on them from the first day. And it isn't a race: if the agent structure feels like too much on day one, a single project session with the write-it-down rule and the quick save is still the right foundation, and the chief of staff can come in a few days later.

## Why this works

Real work teaches the system who you are faster than any amount of configuration, and it teaches you how to drive it at the same time. Putting the agent structure in from the start avoids the slow drift into one enormous conversation that knows a little about everything and forgets most of it, and the write-it-down rule means the system is already accumulating knowledge in files from the first session, rather than starting the habit once the first lesson has been lost.

## Note

This is a sequence, not a schedule. Your projects, your agents, and how fast you move through the stages are yours to set. The durable idea is: *start on real work, with the write-it-down rule, a quick save and the agent structure in from day one, and add everything else only when the work asks for it.* Paste this to your AI and build the version that fits how you work.
